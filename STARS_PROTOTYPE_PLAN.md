# STARS — план создания прототипа (v0.1)

**Дата:** 14 ноября 2026 года  
**Статус:** проектный план, без изменений в GitHub  
**Назначение:** самостоятельная open-source платформа сопоставления спортивных сущностей из независимых провайдеров. EVA DataHub — один из поддерживаемых источников, но не обязательная часть STARS.

## 0. Что должен доказать прототип

Через STARS подключаются **два независимых коннектора**: EVA DataHub (gRPC) и второй REST/fixture-коннектор. Из них поступают команды, названия турниров и компактный контекст матчей. STARS сохраняет локальный индекс исходных записей, находит кандидатов, создаёт канонические команды, сохраняет проверяемые связи и объясняет решения. Повторная загрузка не создаёт дубликатов, а неизменённые записи не запускают матчинг повторно.

**Демонстрационный сценарий:** «Spartak Moscow» из первого источника и «Спартак Москва» из второго отображаются в одной карточке канонической команды; неоднозначное «Динамо» попадает на проверку, а не сливается автоматически.

**Жёсткие ограничения:**

- Не переписывать EVA и не требовать новых RPC от DataHub.
- Не выполнять автоматическое регулярное чтение полного S3 / Parquet ради матчинга.
- Не хранить в STARS коэффициенты и полную историю букмекерских снимков.
- Не ставить отдельные OpenSearch, MongoDB, Redis, Kafka или графовую СУБД.
- Не переписывать старый Rust STARS построчно: старый код — источник тестовых случаев и антипример пересчётов.

## 1. Целевой стек

- \*_C# / .NET 10_, ASP.NET Core — один сервер с gRPC для программных клиентов и HTTP endpoints для админки.
- **PostgreSQL + pg_trgm** — данные, транзакции и индекс похожих имён.
- **Npgsql + EF Core** для CRUD/миграций; параметризованный SQL для поиска и пакетных UPSERT.
- **BackgroundService** и ограниченная очередь заданий в PostgreSQL; один worker на старте.
- **Google.Protobuf / Grpc.Net.Client** для коннектора DataHub; Arrow IPC reader для `ReadDataset`.
- **HttpClientFactory** для REST-коннекторов; конфигурация API и секреты через ссылки на защищённые параметры.
- **React + TypeScript (Vite)** — компактная админка, после работающего backend-сценария.
- **xUnit + Testcontainers** — интеграционные тесты PostgreSQL; OpenTelemetry — базовые метрики.
- Развёртывание: `stars-api` и `stars-postgres` в Docker Compose; worker сначала в API, позже отдельный процесс.

## 3. Последовательность PR

### PR-01. Каркас приложения и инфраструктура

- Создать Solution, проекты, зависимости по слоям.
- Поднять PostgreSQL и `stars-api` через Compose, добавить `/health/live` и `/health/ready`.
- Добавить миграции и начальную конфигурацию, тест подключения к БД, CI build/test.
- **Готово, если:** `docker compose up` запускает сервис с пустой БД и healthcheck успешен.

### PR-02. Source Registry — модель хранения

- Взять разработанную ERD `STARS v0.1` как **логическую основу**, а не копировать весь SQL бесконтрольно.
- Реализовать сначала `provider_connections`, `source_feeds`, `source_entities`, `source_entity_names`, `source_events`, `source_event_participants`, `sync_cursors`, `sync_runs`, `processing_jobs`.
- Ключ источника: `(source_feed_id, entity_kind, source_key)`; при отсутствии внешнего ID не считать одно имя глобальным ключом идентичности.
- Реализовать UPSERT, контроль `identity_hash`, хранение изменений имени, минимального JSONB-контекста.
- **Готово, если:** два импорта одной записи не создают дубль; изменение названия фиксируется; повтор снимка коэффициента не меняет состояние сущности.

### PR-03. Универсальный контракт коннектора

- Интерфейсы: `GetCapabilities`, `ReadSnapshot` (пакеты + cursor/checkpoint), опциональные `ReadChanges`, `GetDetails`.
- Единые DTO: `SourceEntity`, `SourceEvent`, `SourceEventParticipant`, `SourceBatch` с source key, timestamp, версией и provenance.
- Обозначить способы синхронизации: `snapshot`, `since`, `cursor`, `push`; отсутствие `ReadChanges` — нормальный поддерживаемый случай.
- Реализовать тестовый REST/JSON коннектор и fixture-набор с вариантами имён и конфликтами.
- **Готово, если:** второй провайдер подключается без изменения Stars.Core.

### PR-04. EVA DataHub connector (только чтение)

- Создать C# gRPC-клиент из существующего `proto/eva/datahub/v1/datahub.proto`.
- Читать `ReadDataset` с указанием только нужных полей, `snapshot_id`, потоковыми Arrow-пачками и ограниченным размером обработки.
- На первом шаге импортировать ограниченный, настраиваемый объём `api_sport_matches_v1` и одного букмекерского dataset; извлекать команды, турниры, уникальные матчи, но не коэффициенты.
- Сохранять checkpoint, поддерживать безопасный повтор; считать число строк, запросов и объём входящего потока.
- **Готово, если:** данные попадают в Source Registry, а повтор не создаёт дубли; DataHub и EVA не изменены.
- **Важное ограничение:** у текущего DataHub нет полноценного ReadChanges. Поэтому до появления безопасного механизма изменений не включать автоматическую полную периодическую синхронизацию этого коннектора. Для демонстрации изменений использовать fixture/REST-провайдера или ручной ограниченный импорт.

### PR-05. Индексный поиск кандидатов

- Создать `pg_trgm`, B-tree индекс по ключам и типу сущности, GiST/GIN индекс для нормализованных имён.
- Нормализация имени: Unicode, транслитерация RU/EN, базовые сокращения; отдельно сохранять различия U19/U21, женских/резервных составов.
- Поиск сначала exact external ID и уже установленные связи, затем exact normalized name, затем top-K fuzzy кандидатов в рамках вида спорта/контекста.
- **Готово, если:** поиск не сканирует все записи в памяти; неоднозначные команды разных стран или категорий не смешиваются автоматически.

### PR-06. Базовый Matching Engine

- Для кандидатов считать прозрачный score: имя + спорт + соревнование + страна + контекст матча (соперник, начало, домашняя/гостевая сторона).
- Разделить `CandidateGenerator`, `Scorer`, `DecisionPolicy`.
- Создать `match_candidates`, `match_evidence` и сохранение версии правил.
- Для первой версии — только **команды**; соревнования и матчи — контекст. Игроки — отдельный этап после прототипа.
- Не подтверждать автоматически неоднозначные или конфликтующие соответствия.
- **Готово, если:** одинаковый набор входных данных даёт воспроизводимый результат; есть объяснение, почему совпало или не совпало.

### PR-07. Master Registry и управление решениями

- Реализовать `master_entities`, `master_names`, `entity_links`, `match_decisions`.
- Создание канонической команды, ручное подтверждение/отклонение, привязка нескольких source_entities.
- В одной транзакции писать ссылку, решение и evidence; не допускать двух активных канонических связей для одной исходной записи.
- Не переписывать подтверждённые связи при каждом новом наблюдении; при конфликте открывать review.
- **Готово, если:** один master ID объединяет записи двух провайдеров; можно объяснить и отменить связь без потери истории.

### PR-08. Инкрементальная обработка и гарантии

- Из полученного пакета ставить задания только на новые или **значимо изменившиеся** исходные данные.
- Новые доказательства матча должны уметь повторно открыть ранее нерешённое сопоставление, даже если имя не менялось.
- Курсор продвигать только после устойчивой фиксации локальных записей; обеспечить идемпотентные повторные доставки.
- Ограничить параллелизм, размер пачек, память и API-rate limits; добавить retry/backoff и статус синхронизации.
- **Готово, если:** два идентичных импорта подряд не приводят к повторному полному matching и не создают новых связей/решений.

### PR-09. Минимальная админка и внешнее API

- Экран Sources: подключение, включение, ручной Sync, состояние и ошибки.
- Экран Directory: каноническая команда и все исходные имена/ID.
- Экран Review: кандидаты, evidence, подтверждение/отклонение.
- gRPC/HTTP методы для `ResolveBySourceId`, `GetMasterEntity`, `ListMatchesForReview`.
- **Готово, если:** весь демонстрационный сценарий выполняется через интерфейс без SQL.

### PR-10. Проверка прототипа и документация

- End-to-end тест: DataHub + REST fixture → индекс → кандидаты → review → master ID.
- Обязательные кейсы: `Spartak Moscow`/`Спартак Москва`; два разных «Динамо»; смена названия; повторная доставка; потеря соединения; отсутствие стабильного team ID; запоздалое наблюдение.
- Измерить CPU/RAM, объём прочитанных данных, число запросов в DataHub, количество пересопоставлений и качество на размеченном наборе.
- Документировать протокол коннекторов, модель сущностей, ограничения, миграции и команду запуска.
- **Готово, если:** можно воспроизвести прототип из чистой установки и увидеть метрики без ручной настройки SQL.

## 4. MVP — минимальная функциональная граница

Прототип готов, когда:

1. Запускается **отдельным Docker Compose** с PostgreSQL.
2. Подключены два коннектора, один из них — EVA DataHub без изменения EVA.
3. Импорт ограничен, потоковый, возобновляемый; нет автоматического полного опроса S3.
4. Индекс локально ищет кандидатов для команд.
5. В PostgreSQL хранятся source records, короткий контекст событий, master entities, links, evidence и audit.
6. Автоматически не сливаются неоднозначные сущности.
7. Повторный пакет не создаёт дублей и не запускает лишний полный матчинг.
8. Можно через API/админку получить единый ID и список его источников.

## 5. Что намеренно НЕ делать в прототипе

- LLM/векторную БД, ML pipeline и обучение вероятностной модели.
- Полноценный UI-конструктор любых REST API.
- Встроенные произвольные пользовательские DLL-плагины из админки.
- Сложный графовый движок, Kafka, OpenSearch, Kubernetes.
- Полную модель игроков, трансферов и исторических составов.
- Двустороннюю синхронизацию обратно в API провайдеров.

## 6. Первое действие

Начать с **PR-01**, а затем сразу сделать **PR-02 и PR-03** — без алгоритма сопоставления. Сначала доказать, что STARS безопасно и без дублей получает одни и те же спортивные сущности из разных внешних систем. Только потом реализовывать matching.

**Архитектурный риск №1:** отсутствие `ReadChanges` у DataHub. Это не нужно маскировать дорогим таймерным обходом S3. **Архитектурный риск №2:** у некоторых спортивных источников нет стабильного team ID; строку названия нельзя принимать за гарантированную идентичность. **Архитектурный риск №3:** при смене правил нельзя незаметно переписать уже подтверждённые связи.
